# 決策順序

做設計或實作決策時，依序套用以下原則。

## 1. 保證機制的優先順序

要讓某件事「一定正確」時，從最強的保證開始找，能用前面的就不要停在後面：

1. **架構**：用型別與結構讓錯誤寫不出來或編譯不過（例如 `Command` enum 讓指令只能是已知的幾種、typed throws 讓錯誤一定被處理）。
2. **lint／format**：架構擋不住時，用 SwiftLint／SwiftFormat 或檢查腳本在 commit 前擋下（例如 `system_framework_in_wrapper`、`lint-scripts.sh`）。
3. **測試**：靜態檢查做不到時，用單元／整合測試在執行期驗證（例如 `MenuTests` 比對 SwiftBar 的輸出）。
4. **文件／prompt**：以上都做不到時，才寫進 `CLAUDE.md`、`.claude/rules/` 或 skill。

新增任何規範時，先說明為什麼不能用更前面的層級保證；文件只是最後一道，不能取代前面三層。

## 2. 永遠用更新、更簡潔、更安全的做法

- 有新版 API 或語言功能時優先採用（例如 typed throws、async/await 取代 completion handler、Swift Testing 取代 XCTest）。
- 同樣效果下選程式碼更少、概念更少的寫法。
- 優先選編譯期就能檢查的安全做法（型別安全、strict concurrency、非 optional 的存取層）。

## 3. 職責分離，但先算抽象成本

- 職責應該分離；但每多一層抽象、多一個型別或物件，都會增加閱讀與維護的認知負擔。
- 拆分前先確認：這個抽象現在就有第二個使用者或替換需求嗎（例如測試替身、多個實作）？沒有就先不要拆。
- 拆分後的每一層都要有清楚、單一的理由；說不出理由的層就合併回去。

## 4. 提早優化是萬惡之源

- 先寫正確、清楚的版本；有量測證明是瓶頸才優化。
- 不為了「之後可能會用到」預先加快取、併發、泛型或設定開關。

## 5. 每段程式碼都要檢查

寫完或 review 時逐項自問：

- **正確性**：所有路徑（含錯誤、邊界、並行）都正確嗎？有測試或型別保證嗎？
- **可讀性**：第一次看的人能直接理解嗎？命名是否表達意圖？
- **是否足夠簡化**：能刪掉什麼而不影響行為？有沒有多餘的抽象、參數、分支？
- **有沒有成本更低的解法**：既有的型別、系統 API 或專案內已有的工具能不能直接解決？
